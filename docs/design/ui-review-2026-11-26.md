# UI review — send button fix + what the research actually said

Date: 2026-11-26
Owner request: "the send button is now like with words and circle card which look off… most chat ui/ux like messenger, chatgpt, telegram use just arrow logo. so what did you research, learn and study for ui/ux."
Status: send button changed and verified; swipe ask-back deferred by owner ("approve only the send arrow first").

## 1. What was actually wrong

`docs/design/chat-ui-spec.md` §5 said "Send is a circular 44px button, accent-filled only when there is text". It specified geometry and fill, **not the glyph**. I built to the letter of that line and put the word `送信` inside the circle. That is the gap: the spec measured the box and forgot the mark inside it. Nothing in the earlier research covered glyph choice, so the review note in §8 never caught it.

## 2. What the reference apps do (researched 2026-11-26)

| app | mark | container | empty-state behaviour | confidence |
|---|---|---|---|---|
| Telegram Web A | paper plane (`new-send.svg`) | filled accent circle | swaps to mic/record | high — repo source |
| WhatsApp | paper plane | filled accent circle | swaps to mic | medium — teardown |
| Messenger | arrow (outlined) | blue circle | swaps to Like | medium — teardown |
| iMessage | up arrow | filled circle | swaps to mic | medium — Apple docs 429, secondary |
| ChatGPT | up arrow | dark circle | stays visible, muted when empty | medium — screenshots |

Two families, not one: **messaging apps use a paper plane and swap the empty slot for mic/like**, while **iMessage and ChatGPT use an up arrow that stays in place**. The owner asked for the arrow family, so the arrow is correct for this app — and since ours has no voice-message feature, keeping a visible (muted) arrow when empty is the honest version of the pattern.

Sources: `https://raw.githubusercontent.com/Ajaxy/telegram-tt/master/src/components/common/Composer.tsx` (paper-plane asset), W3C WCAG 2.2 SC 2.5.8 (24×24 CSS px target), SC 2.1.1 (keyboard), SC 2.5.7 (dragging alternatives — matters for the swipe card), SC 2.3.3 (`prefers-reduced-motion`).

LINE's quick-reply convention was also checked: bottom-anchored tappable choice pills that disappear once chosen and echo the answer into the thread. That is the Japanese-market precedent for the ask-back card and it reinforces the "swipe plus visible buttons" decision rather than swipe-only.

## 3. What changed

- `app/chat/templates/chat.html` — the button is now an icon-only up-arrow SVG with `aria-label="送信"` and `title="送信"`; it moved **outside** the input pill and is bound back to the form with `form="chat-form"` (the Messenger/ChatGPT layout). The submit handler now keeps `btn.disabled` in sync with the field content, including after a send.
- `app/static/chat.css` — `.composer-row` wraps pill + send with an 8px gap; the pill keeps its 20px radius and 46px height; `.send` is a 44×44 accent circle with an inert grey state (`--line` background, `--muted` arrow) when the field is empty.
- `tests/ui_send.py` — new Playwright check: registers a user, captures the composer empty and typed at 390×844 and 1280×800 in light and dark, measures the button box, and asserts a real `/chat/send` request plus the optimistic bubble when the arrow is clicked.

## 5. Why you have not seen me test the UI like the agents on X

Two different things were missing, and only one was a capability gap.

- The capability existed. `tests/ui_capture.py` drives the real app with Playwright: it registers, types, clicks send, waits for the AI, screenshots every step and records a video into `documents/_extract/ui/`. It has been in the repo since the chat work started.
- What was missing is **visibility**. Those runs happened in previous sessions, the files landed in `documents/_extract/`, and I reported pass/fail sentences instead of showing the frames. That is my failure of reporting, not a missing tool.
- The other real gap: no check was tied to a *specific* UI change, so nothing was guaranteed to run and be shown for a fix like this one. `tests/ui_send.py` closes that for the composer: it is small, runs in ~20s, and prints measured boxes and the screenshot path.
- Still missing vs. the X demos: no live browser the owner can watch in real time, and no video for this change. `ui_capture.py` already records video; the composer check can be extended to do the same when the ask-card lands.
